JWT Token Structure — header.payload.signature

Header (JOSE)
{
  "alg": "RS256",
  "typ": "JWT",
  "kid": "<key-id>"
}
Payload (Claims)
{
  "sub": "user-uuid",
  "iss": "https://auth.../realms/tenant",
  "realm_access": {
    "roles": ["ADMIN", "USER"]
  },
  "exp": 1712345678,
  "iat": 1712345378,
  "azp": "secufusion"
}
Signature
RSASHA256(
  base64UrlEncode(header) + "." +
  base64UrlEncode(payload),
  RSA_PRIVATE_KEY
)

✓ Verified via JWK Set URI
/realms/{realm}/protocol/openid-connect/certs

🔄 JWT Authentication Flow — Step by Step

Complete login-to-access flow across Frontend, Backend, and Keycloak

1
User Opens Portal
User navigates to the web portal and enters login credentials (username + password)
Frontend
2
Frontend → Backend
Frontend sends POST /api/iam/auth/login with credentials to the API Gateway over HTTPS
Frontend → Gateway
3
Backend → Keycloak
IAM service forwards auth request to Keycloak's OIDC token endpoint for the tenant's realm
Backend
4
Keycloak Validates
Keycloak validates credentials against the realm user store; issues JWT access token (5 min) + refresh token (30 min)
Keycloak
5
JWT Returned
JWT tokens flow back: Keycloak → IAM Service → Gateway → Frontend. Login audit event recorded.
Backend → Frontend
6
JWT Stored
Frontend stores access + refresh tokens. Every subsequent API request includes Authorization: Bearer <token>
Frontend
7
JWT Validated
Each service validates JWT: verifies RS256 signature via JWK Set URI, checks expiry (exp), issuer (iss), audience (azp)
Backend (per-service)
8
RBAC Check
Backend extracts roles from realm_access.roles claim. Checks against 38 defined scopes for endpoint-level authorization
Backend
9
Access Decision
Access granted ✅ or denied ❌ (403 Forbidden) based on role. Roles: MASTER_MSSP_ADMIN, MSSP_ADMIN, ENTERPRISE_ADMIN, USER, VIEWER
Backend
10
UI Rendered
Response returned to Frontend. UI conditionally renders based on user's role — admin sees full dashboard, viewer sees read-only
Frontend
